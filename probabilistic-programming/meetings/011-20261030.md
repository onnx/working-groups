## Quick Recap
The meeting reviewed feedback from the ONNX Operators SIG on the RNG proposal and its implementation pull request ([onnx/onnx#8420](https://github.com/onnx/onnx/pull/8420)). The discussion clarified how seeding and entropy fit into the stateless PRNG design, why a specific PRNG algorithm (Threefry) is proposed, and how much determinism can be guaranteed across hardware platforms. A draft roadmap for Q4 2026 and 2027 was outlined. It starts with the RNG pull request, then adds more sampling operators and distributions, and later covers probabilistic-programming and inference support. Longer-term questions covered whether inference algorithms belong in the ONNX specification or in framework converters, and what an ONNX Runtime implementation will involve.

## Key Outcomes
* **Entropy stays outside the specification.** The proposal adds a deterministic *pseudo*-random number generator, not a true random number generator. The seed is supplied by the user as an ordinary graph input and is converted into a PRNG state by `InitPRNG`.
* **Determinism is specified at two levels.** PRNG state transitions must be bit-exact on every platform. Sampled floating-point values that involve transcendental functions (e.g. `RandomNormal` via the Box–Muller transform) only need to agree across platforms within a tolerance. An attempt should be made to define that tolerance.
* **The Threefry choice needs a written rationale.** The Operators SIG asked why Threefry was selected over alternatives; a comparison will be added to the proposal.
* **Scope of the first pull request.** The new PRNG state operators and the updated `RandomNormal`, `RandomUniform`, `RandomNormalLike`, and `RandomUniformLike` are submitted together, so they can be reviewed and merged as one unit (target: Q4 2026).
* **Roadmap process.** The roadmap draft will be discussed in the WG Slack channel before it is submitted as a pull request to the overall ONNX roadmap.

## Discussion

### 1. Operators SIG Feedback on the RNG Proposal
The RNG proposal and PR #8420 were discussed at the previous week's Operators SIG meeting; notes from that meeting are in the WG Slack channel. Two main questions came back.

#### 1.1 Why Threefry?
The SIG asked whether alternatives had been reviewed before a specific algorithm was selected and requested a written justification. The alternatives discussed:

* **Threefry**: counter-based; the default PRNG in JAX. Its state contains an integer counter that is incremented.
* **Philox**: counter-based; used by PyTorch and available as an option in JAX. Not yet examined in detail by the WG.
* **Java's generators (SplitMix and the LXM family)**: developed at Oracle Labs and extensively tested. They are not counter-based in the same way as Threefry. SplitMix applies a hash (mixing) function to an internal value that behaves somewhat like a counter. It uses two different mixing functions: one to advance the seed when the generator is split, and one to advance it when values are generated. The LXM generators combine a linear congruential generator with a mixing function.

The existing argument for Threefry (a mature, well-tested implementation in JAX; see the meeting of Jun 12, 2026) should be expanded into an explicit comparison with these alternatives.

#### 1.2 Should the Specification Contain a Random Number Generator?
The SIG noted that the proposal contains no actual random number generator (entropy source). It asked whether a section on random number generation and seeding should be added, possibly with a generator inside the specification. Adding a generator to the specification would run against the architectural direction of the proposal. Key points of the discussion:

* **Keeping entropy external is the central design goal.** Today each ONNX implementation is free to choose how the random operators behave, and the implementations have diverged. For example, when `RandomNormal` is used without a `seed`, the specification does not define what happens; implementations do *something*, but the specification does not control what. The proposal closes this gap so that everything is deterministic given the inputs, like the rest of ONNX.
* **Operators transform state.** The proposed operators are pure functions that turn a PRNG state into a new PRNG state, from which values can be sampled.
* **`InitPRNG` is the entry point for entropy.** It maps any user-chosen seed to a valid PRNG state; the entropy in the system is exactly the seed the user chose. This mapping is deliberate. Generators such as Java's pass every seed through a hash function before using it as state, because during the pre-release development of a Java 8 generator some seed values produced poor-quality output: they did not have enough set bits in the right places. Transforming the seed moves those bits around and avoids such bad states. The mapping could in principle be the identity function, but probably will not be for the candidate algorithms. It is a hook that gives users a way, within ONNX, to produce a correct state, and `InitPRNG` may live in a separate graph from the one that consumes the state.
* **The seed is a regular graph input.** In ONNX Runtime, ONNX-MLIR, or any other implementation, the user supplies a seed (or PRNG state) in addition to the inputs of the neural network or other computation.
* **`RandomUniform` already is a random number generator**, and much can be built on top of it. One caveat was raised: rejection samplers (e.g. for the gamma distribution and some normal samplers) loop an unbounded number of times until a value falls within a range or crosses a threshold. The view was that this cannot be expressed as an ONNX function, so not every sampler can be an ONNX function wrapping `RandomUniform`.
* **Non-reproducible seeding is the user's choice.** When reproducibility does not matter, a seed can be drawn from the operating system's entropy source (e.g. a non-blocking `/dev/urandom`), a timestamp, or similar.
* **Open question: `InitPRNG` without a seed.** A no-argument variant that uses a timestamp would help usability. As a separate, explicit operation, it would at least make users choose it consciously, and the value could be recorded. The counter-position: a library should not invent a seed. It should require one or fall back to a single fixed, non-time-based default, because non-reproducible behavior by default causes real problems in practice. The current proposal defines `InitPRNG` with a required `seed` input.

#### 1.3 Terminology
The proposal text mentions a "source of randomness" and "deterministic generation". This was found confusing, since the proposal adds a *pseudo*-random number generator and every PRNG is deterministic. The intended meaning:

* Randomness is no longer part of the specification; users bring their own entropy in the form of a seed.
* Where the seed came from does not matter. Given the same seed, everything downstream of that interface is deterministic and reproducible.

The wording should be revised to say this directly.

### 2. Determinism versus Cross-Platform Reproducibility
Proposed position for the specification:

* **PRNG state transitions:** a given input state must produce exactly the same output state on every platform.
* **Sampled values:** for operators involving transcendental functions, such as `RandomNormal` (the Box–Muller transform uses sine and cosine), results should agree across platforms within a tolerance, e.g. 1–2 units in the last place (ULP), rather than bit-for-bit. It is not yet clear whether the tolerance can be pinned down in the specification, but an attempt should be made.

The distinction is between determinism and cross-platform identity. On one platform, the same inputs always produce the same values. Across platforms, `RandomNormal` called with state *s* returns the same successor state *s'* everywhere, and sampled values that are very close but not necessarily identical (e.g. CPU versus CUDA).

Rationale:

* Bit-identical double-precision results would require identical implementations of sine and cosine on NVIDIA GPUs, AMD GPUs, and in CPU code from different C and C++ compilers. Even different NVIDIA generations (A100, H100, B200) return different results for some functions.
* Implementations of transcendental functions sit deep in the software stack and change without notice. Compiling C code with fast-math enabled changes results, and it is unclear by how much, because the compiler starts rearranging the computation.
* Two examples were discussed:
  * A production team upgraded TensorFlow (possibly only a patch release), and their model outputs changed because the order of floating-point operations in the computational graph changed. CI tests with overly tight tolerances failed. Running on a GPU would also have produced different results.
  * In earlier work on a reproducible machine-learning library, a linear model was trained on MNIST with AdaGrad on x86 and on Apple ARM, each with Java 8 and Java 11. The resulting models classified roughly 50–100 of the 10,000 test samples differently. The code was identical; only the `exp` and `log` implementations differed between platforms and Java versions (the change happened in Java 9), even though the Java specification constrains these functions fairly tightly. Such differences cannot be fixed, only documented.
* **Conclusion:** reproducibility is achievable on the same hardware, operating system, and software stack. Across platforms, the specification should guarantee the sequence of states and bound the differences in values, not require identical values. The WG's existing proposal document already contains language along these lines ("Revised Determinism Language"); it should be stated explicitly in the proposal and the PR.

### 3. Roadmap Draft
A roadmap covering roughly the next year was requested as input for the overall ONNX roadmap. A first draft has been prepared and shared within the WG leads; it will be posted in Slack for discussion. A clear picture of where the work is heading also helps reviewers when getting the RNG pull request merged.

**Overall sequence of the work**
1. Fix the random operators currently in the specification, so that sampling is reproducible. Without that, a probabilistic programming system running on ONNX is not reproducible and therefore of little use.
2. Expand the set of sampling operators.
3. Add distribution support: sampling, and computing log-probabilities for a given parameter setting and input.
4. Add support for running probabilistic programs and inference algorithms (sections 4 and 5).

Everything after step 1 critically depends on the RNG specification and its determinism, so that comes first.

| Period | Planned work |
|---|---|
| Q4 2026 | Initial RNG pull request: the new PRNG state operators together with the updated `RandomNormal`, `RandomUniform`, `RandomNormalLike`, and `RandomUniformLike`, reviewed and merged as one unit. |
| Q1 2027 | Additional sampling operators that PyTorch provides as built-in operations outside `torch.distributions` (`torch.multinomial`, `torch.bernoulli`, `torch.poisson`). |
| 2027 | Distributions, a demo converter, and the ONNX Runtime implementation (details below). |
| Later | Probabilistic-programming operations and inference algorithms (sections 4 and 5). |

**Q1 2027: sampling operators**
* The PyTorch built-ins are a natural first set because they are separate from `torch.distributions`, which offers many more distributions, several of them considerably more esoteric.
* ONNX already has `Multinomial` and `Bernoulli`. They should be brought in line with the explicit PRNG state model, possibly in a second pull request rather than the first. `Multinomial` is likely also of interest to the GenAI WG.
* `Poisson` would be a new operator. It is a very standard sampling operation used in many places. The argument to the Operators SIG: ONNX already has `Bernoulli` and `Multinomial`, and `Poisson` should behave the same way. It may be awkward to express in plain ONNX because of looping (to be checked).
* These are proposed as core ONNX operators because they are broadly useful; how much the Operators SIG is willing to accept remains to be seen.
* `Dropout` also consumes randomness; how to handle it is undecided.

**2027: distributions and tooling**
* Determine which further distributions are needed for reasonable coverage by analyzing a set of real Stan (and other PPL) programs. Likely candidates: Beta, Dirichlet, Gamma, and Inverse Gamma.
* Define what a "distribution" is in the specification. One option is independent operators for log-probability and for sampling, with no relationship between them in the spec. The alternative is to introduce some formal notion of how they relate.
* Testing: validate sampling behavior against NumPy and against SciPy's distribution definitions. Real probabilistic programs could also serve as a basis for tests.
* Build an initial converter to use for demos.
* After the specification PR, submit an ONNX Runtime PR (see section 5).

**Later: probabilistic-programming operations**
* Probabilistic programs repeatedly sample and evaluate the likelihood. An open question is whether ONNX needs dedicated operators for likelihood evaluation, or whether the PPL that exports the ONNX graph should build that computation itself. The analogy: ONNX has no "forward" operator; PyTorch writes the forward pass as an ONNX graph during export, and training tools write the backward graph.
* This is the part of the probabilistic-programming work the WG ultimately wants to reach.

### 4. Inference Algorithms: Specification or Converter?
The total amount of work for inference algorithms is roughly fixed, but it can be placed in two different places:

* **In the ONNX specification:** complex operators that perform, for example, a full Hamiltonian Monte Carlo (HMC) update: simulate a particle trajectory through the parameter space for a number of steps, reflect it at the constraint boundaries, and then apply a Metropolis acceptance step. This is a very large and complicated operator, and every ONNX implementation would have to implement it.
* **In converters:** each probabilistic programming system (Stan, TensorFlow Probability, Pyro, NumPyro, ...) gets Python code that emits a sequence of ONNX operators performing the whole HMC step. This work then has to be repeated for every PPL.

The trade-off is whether an algorithm can be expressed in the specification at all, and how unpleasant the resulting operator would be. Neither extreme is attractive. The likely outcome is a middle ground. Dedicated operators would cover only the critical parts that cannot be expressed in ONNX, such as the trajectory integration. Parts that can be built from standard ONNX operators, such as the Metropolis–Hastings test, would become ONNX functions or be inserted by the converter. The goal is to find the split that minimizes the combined work for specification implementers and converter authors. Work on this part has not started yet, and several steps come before it.

### 5. ONNX Runtime Implementation and Performance
* If the updated `Random*` operators can be defined as ONNX functions, ONNX Runtime only needs to be pointed at the function definitions to get a basic implementation. That needs no per-platform work, but it will likely be slower than specialized kernels. The ONNX Runtime developers will be asked what they prefer; if more work is needed, contribution approvals for ONNX Runtime are already in place within the WG, which makes that work easier.
* A first-pass native implementation is conceptually straightforward. For each execution provider, a kernel is implemented and registered under the operator name and version. That still means fairly tricky C++, CUDA, or ROCm/HIP code.
* ONNX Runtime contains a lot of machinery that specializes execution: optimization passes and graph transformations. Improving beyond a first pass means working out which transformations and passes would help. That level of compiler and runtime expertise is currently not available in the WG.
* Some probabilistic-programming operations resemble computations that ONNX Runtime already accelerates well. Sampling procedures do not: there is little to accelerate today and little demand for speed. Bringing sampling-heavy workloads to ONNX would make this more important.

## Open Questions
* Threefry versus Philox versus other algorithms: what is the documented rationale?
* Should `InitPRNG` offer a no-seed (timestamp-based) variant, or always require a seed?
* What tolerance should the specification set for sampled values across platforms?
* How should `Dropout` be treated under the explicit PRNG state model?
* Can `Poisson` and rejection-based samplers be expressed in plain ONNX?
* Should the specification relate log-probability and sampling operators for the same distribution?
* Should likelihood evaluation be dedicated operators, or graphs generated by PPL exporters?
* Where should the split between specification operators and converter-generated graphs lie for inference algorithms such as HMC?
* Should ONNX Runtime rely on function-based implementations of the random operators, or provide specialized kernels?

## Quick Recap
The meeting focused on getting the RNG pull request ([onnx/onnx#8420](https://github.com/onnx/onnx/pull/8420)) merged before the ONNX 1.24 branch cut on Dec 1, 2026. It discussed whether Philox should be specified alongside Threefry, and why every additional PRNG algorithm adds to the burden on ONNX implementations. The proposed way to limit that burden is to express as much as possible as ONNX functions. The core would be `InitPRNG`, `SplitPRNG`, `RandomUniform`, and `RandomUniformLike`, with `RandomNormal` and other samplers built on top. Implementations such as ONNX Runtime could then inline the function bodies instead of writing their own kernels, as they already do for other function operators. Samplers that need rejection sampling are the exception. The meeting also returned to the question of how much determinism the specification should require. A recently published analysis, which identifies the GPU architecture a model was trained on from its Philox sampling behavior, served as the example.

## Key Outcomes
* **Merge target for PR #8420 is the 1.24 branch cut (Dec 1, 2026).** The PR passes all tests. It needs approval from the Operators SIG, which does not meet again until January 2027, so approval will be requested in Slack. The timeline is tight.
* **Direction: Threefry as the only algorithm in the first PR.** Once the PR is merged, the algorithm choice becomes part of the specification and must not be walked back soon after. Settling on Threefry allows an earlier merge. Philox will be examined before any decision to add it. Whether the Philox code that has already been written should go into the PR is still open.
* **Caution about additional algorithms.** Every algorithm in the specification must be implemented by every implementation that claims conformance. A second algorithm is much less of a burden if it can be provided as ONNX functions that implementations can take over unchanged. Otherwise it needs native support in every implementation.
* **Compose the sampling operators as ONNX functions.** `InitPRNG`, `SplitPRNG`, `RandomUniform`, and `RandomUniformLike` form the core. `RandomNormal` (Box–Muller) and further samplers are built on `RandomUniform` as ONNX functions where possible. Samplers that need rejection sampling (e.g. Poisson, gamma) are the exception.
* **Reproducibility, not perfect determinism.** The specification should require a certain amount of reproducibility, but not so much that it forces fixed parallelism or makes implementations slow or difficult. It must not promise identical sampled values across CPUs and GPUs. This confirms the position from the meeting of Oct 30, 2026.

#### 1.2 Does Merging Require Consensus on Threefry?
Once the PR is merged, its content is part of the specification. The algorithm choice therefore has to be one that will not be walked back soon after. The choice of algorithm has also come up in the review of the PR, and one review comment has not been answered yet.

Editorial note: the review comments on PR #8420 (Sep 20 and Oct 19, 2026) propose a mandatory `algorithm` attribute on the PRNG operators, with `"threefry2x32-20"` as the only allowed value for now. The Oct 19 comment is the one that has not been answered yet.

### 2. Threefry, Philox, and the Cost of Multiple Algorithms

#### 2.1 Philox as a Second Algorithm
Philox was brought up as an alternative to Threefry. It is used in PyTorch, where it is the default generator on CUDA devices, which is a good sign. It was also noted to be used in TensorRT, which some of this work may eventually target. Code for Philox has already been written. One option is to add both Threefry and Philox to the specification.

#### 2.2 The Burden on Implementations
* Every algorithm in the specification has to be implemented by every implementation that wants to claim conformance to that ONNX version. Besides the ONNX reference implementation, there are at least three independent implementations, among them ONNX Runtime and ONNX-MLIR.
* All of them depend, or can depend, on the ONNX C++ code. If ONNX provides the init, split, and `RandomUniform` operations as ONNX functions (plus `RandomUniformLike`, which is needed because of how the output shape is determined), implementations can take those definitions as they are. Their remaining work is to use the operator definitions from the ONNX library instead of their own. That is expected to be easier than what they currently do.
* Samplers that cannot be expressed as ONNX functions interact with the low-level PRNG behavior directly. Every additional algorithm would then need native support in all implementations, and implementations may not be willing to provide it. This is the main reason for caution about adding algorithms.
* Philox should therefore be examined first: what it does, whether it is suitable, and whether it can also be expressed as a function. If it can, downstream libraries can take it over directly.

#### 2.3 Current ONNX Runtime Behavior
Adopting the new operators will require code changes in ONNX Runtime. Today, each random operator node in ONNX Runtime contains a complete C++ random number generator. That generator keeps its state across runs, and it is unclear how the state is used and how operations on it are serialized. This is part of the problem the proposal addresses (see the "ONNX Runtime" section of the [RNG proposal](../documents/rng_proposal_july_06_2026.md)).

### 3. Composing the Sampling Operators as ONNX Functions

#### 3.1 Layering on `RandomUniform`
Once init, split, `RandomUniform`, and `RandomUniformLike` exist, everything else should be built on top of them, as ONNX functions as far as possible:

* `RandomUniform` provides the entropy. Once it delivers the required number of uniform random bits (e.g. 64 or 128), other samplers can wrap a call to it: the Box–Muller transform for Gaussians, or the gamma-based transforms needed for sampling Dirichlet distributions.
* The next step is therefore to rewrite `RandomUniform` and `RandomNormal` as functions. `RandomUniform` comes first, because everything else builds on it.
* Function-based definitions make the operators easier for every implementation to adopt.

#### 3.2 Limits: Rejection Sampling
Some samplers cannot be written as a call to `RandomUniform`:

* They need unbounded loops: they keep sampling until a value falls within a particular range. Examples are Poisson and samplers that need gamma variates, which effectively perform rejection sampling. The view was that such loops cannot be expressed as an ONNX function, because the ONNX computation graph is not Turing complete.
* Such an operator cannot get its entropy from a call to `RandomUniform`. It has to contain its own implementation of Threefry (or Philox), and so does every further operator of this kind. The algorithm then moves into the core of every implementation of the specification.
* Implementations may pull that code from ONNX, and the ONNX code should be designed to make that easy. However, the reference implementation is written in Python. ONNX Runtime cannot consume a Python implementation, and ONNX-MLIR also needs a C++ implementation. Even with a C++ implementation, ONNX Runtime cannot move such an operator to a GPU or another accelerator unless a dedicated implementation exists, for example in CUDA.

#### 3.3 How Function Operators Work
* The ONNX C++ definition of the `Gelu` operator was used as an example. It builds a function body from a series of existing ONNX operators and emits it as the operator's function. A library that consumes the definition can pull in that implementation and get a result that is close enough. The sequence operators are further examples, but they are considerably more complicated.
* The Threefry split operation and the sampling operations can very likely be expressed the same way, as a series of existing ONNX operators. All implementations could then pull in the definition and run it through their existing optimization pipeline. The WG would not have to implement or optimize a kernel for any backend.
* ONNX Runtime has specialized implementations of operators that are used heavily, such as `Gelu`, which is integral to transformer models. For other operators, such as the sequence operators, it has no kernel of its own. If a function definition exists for the operator, ONNX Runtime pulls in that definition and uses it. This works for CPU and CUDA alike, because the result is a set of ONNX operators that ONNX Runtime already knows how to compile and optimize.
* This may be slower than dedicated kernels, but it is expected to be fast enough. Users who rely heavily on the random number generation operators can then be approached about faster implementations, and they may want to contribute.
* The approach should work for all operators currently planned, but not for Poisson and other samplers that need gamma variates or repeated sampling. It makes the initial part of the work much simpler.

Editorial note: the proposal document currently lists the new and updated operators with `function: False`.

### 4. Determinism, Parallelism, and Hardware Fingerprinting

#### 4.1 Fingerprinting Training Hardware via Philox
A recently published analysis, discussed on Hacker News (link in the WG Slack channel), showed the following:

* The way NVIDIA's warp scheduler distributes work makes it possible to infer how many CUDA cores executed a particular operation.
* If the random number generation algorithm is known to be Philox, the seeds can be swept. Once the seed of the first draw is found, the 4–5 different layout variants that exist for different GPU architectures can be tried. Because the architectures have different numbers of compute cores, the computation is laid out differently on each of them.
* This identifies, with reasonable confidence, the GPU architecture a model was trained on. The analysis points out that some companies are not supposed to have access to Blackwell GPUs.

#### 4.2 Consequences for the Specification
* Determinism and knowledge of the sampling algorithm are extremely useful. However, the analysis is also a reason not to aim for complete, perfect determinism in the specification. That would require sequentializing these operations, and implementations would not be allowed to change the amount of parallelism available to them: it would have to be fixed at all times.
* The analysis shows that the output of such a system depends strongly on the hardware platform. A specification that claimed otherwise would create different problems.
* The question was raised whether Philox or Threefry could be designed or used so that this kind of fingerprinting is impossible. That is very likely possible, but possibly not with the same degree of parallelism. Making full use of the available CUDA cores is not trivial.
* Parallel sampling algorithms that are agnostic to the compute shape exist and give the same answer for every compute shape. However, they need a certain amount of built-in overhead to enforce that behavior. Example: a split operation inserted along the batch axis gives every batch element a fresh PRNG state. This initial split defines the shape and structure of the random number generation, and the parallelism follows it. The results are identical no matter how many threads are available, and the scheme is robust to fingerprinting. The split has to be computed first, though, which adds overhead, and the scheme does not necessarily exploit all available parallelism. (Editorial note: per-batch-element PRNG states were also discussed in the review of PR #8420 on Sep 20 and 27, 2026.)
* Machine learning has traditionally resolved this trade-off in favor of speed, which leads to poor reproducibility. The WG's goal is to push back on that lightly: to specify a certain amount of reproducibility and determinism, but not so tightly that the operators become slow or difficult to implement.
* For example, Gaussians sampled via `RandomNormal` will not necessarily agree to 16 decimal places between CPUs and GPUs, so the specification must not promise that. This matches section 2 of the notes of the [Oct 30, 2026 meeting](011-20261030.md) (determinism versus cross-platform reproducibility).

* Should the PRNG operators carry a mandatory `algorithm` attribute, as proposed in the PR review?
